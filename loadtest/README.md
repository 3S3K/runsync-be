# 동시 사용자 부하 테스트

실시간 위치 공유(WebSocket)와 러닝 세션 API가 여러 사용자가 동시에 접속한 상황에서 정상 동작하는지 확인한다.

## 시나리오

가상 사용자마다 아래 흐름을 수행한다.

```
WebSocket 접속 → 러닝룸(협동 러닝) 구독 → 러닝 시작 → GPS 송수신 → 러닝 종료 → 기록 저장
```

- 모든 사용자가 접속을 마친 뒤 동시에 달리기 시작한다.
- GPS는 1초마다 전송한다. 러닝룸에서는 한 사람이 보낸 위치를 참가자 전원이 받는다.
- 실제 앱처럼 5초마다 누적 거리·시간을 저장한다(REST).

## 실행

Node 22 이상이면 되고, 설치할 패키지는 없다.

```bash
# 가상 계정 모드 (로컬): 계정마다 토큰을 직접 만든다. 서버와 같은 JWT_SECRET 이 필요하다
JWT_SECRET=... node load-test.mjs --target http://localhost:8090 --users 50 --first-user-id 3 --room 1 --server-pid <서버 PID>

# 단일 계정 모드: 한 계정의 토큰으로 연결 수만 늘린다 (러닝 세션·러닝룸 없이 접속과 송수신만)
ACCESS_TOKEN=... node load-test.mjs --target https://api.example.com --users 50
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--target` | `http://localhost:8090` | 대상 서버 |
| `--users` | 5 | 가상 사용자(동시 연결) 수 |
| `--duration` | 30 | GPS 송수신 시간(초) |
| `--interval` | 1000 | GPS 전송 주기(ms) |
| `--first-user-id` | 1 | 가상 계정의 첫 사용자 번호 (가상 계정 모드) |
| `--room` | 없음 | 러닝룸(협동 러닝) 번호 |
| `--server-pid` | 없음 | 주면 서버 프로세스의 CPU·메모리를 함께 측정 |

로컬 준비와 정리는 `local-setup.sql`, `local-cleanup.sql` 을 쓴다. 가상 계정 100개와 진행 중인 러닝룸 1개를 만들고 지운다. **로컬 DB에서만 실행한다.**

## 결과 (로컬, 2026-11-28)

| 동시 사용자 | 접속·러닝 시작 | 위치 전송 | 수신(전송 × 참가자) | 전송 성공률 | 지연 평균 | 지연 p95 | 지연 최대 | 종료·기록 저장 | 서버 CPU 평균 / 최대 | 서버 메모리 최대 |
|---|---|---|---|---|---|---|---|---|---|---|
| 5명 | 100% | 150건 | 750건 | 100% | 7ms | 17ms | 20ms | 100% | 3% / 21% | 515MB |
| 10명 | 100% | 300건 | 3,000건 | 100% | 9ms | 25ms | 34ms | 100% | 4% / 18% | 475MB |
| 50명 | 100% | 1,500건 | 75,000건 | 100% | 33ms | 58ms | 84ms | 100% | 15% / 41% | 477MB |
| 100명 | 100% | 3,000건 | 300,000건 | 100% | 112ms | 188ms | 248ms | 100% | 52% / 89% | 538MB |

- 네 단계 모두 접속, 러닝 시작, 위치 전송, 주기 저장, 러닝 종료, 기록 저장에서 실패가 없었다.
- 테스트 후 DB를 확인했다. 러닝 기록 170건(시험 실행 5건 포함), 경로 5,000건이 전송한 위치 수와 일치했고, 종료되지 않은 세션은 0건이었다.
- 서버 로그에 요청 처리 오류는 없었다.
- 지연은 인원이 늘수록 커진다. 러닝룸은 한 사람의 위치를 전원에게 보내므로 전달량이 인원의 제곱으로 늘어난다(100명에서 초당 약 10,000건).

## 측정 조건과 한계

- **로컬 환경의 결과다.** 서버·DB·Redis·테스트 클라이언트가 모두 같은 장비(Apple M4, 10코어, 16GB)에서 돌았다. 운영 서버(EC2 1대)의 처리 한계를 나타내지 않는다.
- CPU 수치는 코어 하나를 100%로 본 값이다(10코어 장비에서 최대 1,000%).
- 지연 시간에는 테스트 클라이언트가 메시지를 처리하는 시간이 포함된다. 가상 사용자 100명이 한 프로세스에서 초당 10,000건을 받아 해석하므로, 인원이 많은 단계의 지연에는 클라이언트 쪽 부하가 섞여 있다.
- 네트워크 지연이 없다. 실제 모바일 환경에서는 여기에 왕복 지연이 더해진다.
- SQL 로그 출력을 끈 상태로 측정했다.
- 한 러닝룸에 전원이 들어가는 가장 불리한 경우다. 실제로는 여러 러닝룸에 나뉜다.
- 연결이 끊겼다가 복구되는 시나리오는 포함하지 않았다.
